# BroadcastContentAutomation Tests

Regression suite for the Trendline Now pipeline (and the shared helpers it
is built on). Every test pins a behavior a past fix established, so a future
change that breaks one fails loudly here instead of shipping a broken video.

## How to run

On a normal machine (or CI), the standard runner works:

```
dotnet test Tests/BroadcastContentAutomation.Tests.csproj -c Release
```

In this sandbox, `dotnet test` cannot start its testhost (the testhost IPC
channel is blocked, so the run times out after 300s). Use the console
runner instead — it executes the same xUnit `[Fact]` methods directly:

```
dotnet run --project Tests.Runner -c Release
dotnet run --project Tests.Runner -c Release -- <filter-substring>
```

Exit code 0 = all pass, 1 = any failure.

## How the internals are reached

`Shared` (Text, SeoScore, Sidecar) is public and referenced directly.
VideoGen's pure logic lives in top-level local functions (`BuildChapters`,
`CanonicalHashtags`, `WithCanonicalHashtags`) and `ScriptGenerator`
(`NormalizeTag`), which a test project cannot reference directly. Those are
reached through `ReflectionHelper` (find-by-substring on the built DLLs) —
the same pattern the fix-verification harnesses used. Uploader internals
are reached the same way: the publishers are internal classes, so tests
construct them and invoke their private methods (`CheckPriorVideoAsync`,
`WaitForPublishAsync`, `ReconcileCrossLinksWithServiceAsync`) via
reflection, driving them with canned `HttpMessageHandler`s (Meta/TikTok)
or a canned `IHttpClientFactory` (YouTube, whose client gzips request
bodies — the fake handler decompresses them). If a pure function is
ever extracted to `Shared` as a public static method, call it directly and
drop the reflection lookup for it.

Tests that need real video data read `work/trendlinenow/job-*/script.json`
from their absolute paths and skip gracefully if the files are missing.
No test touches the network, a real API, or a render.
